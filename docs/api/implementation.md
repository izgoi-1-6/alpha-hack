# Implemented foundation interfaces

Task 2. Root paths below are relative to this repository. The canonical contract is `docs/superpowers/specs/2026-10-24-credit-route-design.md`; these are concrete reusable interfaces for subsequent modules. Add new routers under `/api/v1` in `backend/app/main.py`.

## Backend dependencies and transactions

- `app.db.Base`: SQLAlchemy declarative base. Add models to the same metadata and import them from Alembic `migrations/env.py` before generating new revisions.
- `app.db.engine`, `SessionLocal`: configured by `DATABASE_URL`, default PostgreSQL+psycopg on localhost. `SessionLocal` uses `expire_on_commit=False`.
- `app.db.get_db() -> Generator[sqlalchemy.orm.Session, None, None]`: one request transaction; commits after successful endpoint, rolls back on exceptions. Endpoints call `flush()` when IDs/constraints are needed. Do not commit halfway through business commands. Error `Response` returns still commit (used to persist failed login attempts). Script callers use `with SessionLocal.begin() as db:`.
- `app.identity.Db = Annotated[Session, Depends(get_db)]`, `Now = Annotated[datetime, Depends(utc_now)]` are reusable FastAPI aliases.
- `app.clock.utc_now() -> datetime`: UTC wall clock; tests override `app.dependency_overrides[utc_now]`. `as_utc(datetime) -> datetime` handles SQLite's naive adapter timestamps; `iso_utc(datetime) -> str` writes UTC `Z`. Fixture reference dates are exclusively business dates.
- Migrations: `477de883cdb2` (identity/company/consent/idempotency entities) and `070eeaa75839` (precheck sequence). Apply with `backend/.venv/bin/alembic -c backend/alembic.ini upgrade head`. API startup does not create tables.

## Identity and ownership

- `app.identity.get_current_user(request: Request, db: Db, now: Now) -> User`: resolves SHA-256 digest of the opaque cookie, rejects revoked/expired sessions at 401; never accepts role/owner from request bodies.
- `CurrentUser`, `ClientUser`, `OfficerUser` are `Annotated[User, Depends(...)]` aliases. `require_client(user: CurrentUser) -> User` and `require_officer(user: CurrentUser) -> User` enforce roles with 403. New officer routes must use `OfficerUser`; owner routes use `ClientUser`.
- `app.companies.get_owned_company(db: Session, company_id: str, user_id: str, *, for_update: bool=False) -> Company`: combines owner/resource predicates, 404 for foreign or absent resources. `for_update=True` acquires the PostgreSQL row lock. Call it before idempotency replay on company commands. No general officer bypass is included; officer routes must enforce their own explicit read policy.
- `app.identity.public_user(User) -> dict`: only id/email/display_name/role. `password_hasher` is Argon2id. Raw passwords and raw cookie tokens are never persisted. Cookie name is `credit_route_session`; fixed expiry 12 hours, revoked on logout. No sliding extension. Multiple login sessions are independent.
- Global `check_origin(request: Request) -> None` enforces exact `settings.ui_origin` on POST/PUT/PATCH/DELETE including auth. CORS allows that origin with credentials. `Cache-Control: no-store` and `nosniff` apply to API responses. Vite/nginx proxy `/api`.
- Failed logins are DB-persisted buckets keyed by hash(email + peer address), limited to ten failures per fifteen minutes. This is a demo bound, not production abuse protection.

## Models and sources

`app.models` exports `User`, `AuthSession` (table sessions), `LoginAttempt`, `Company`, `Precheck`, `Consent`, `IdempotencyRecord`, `new_id() -> str` (UUID4). UUIDs are stored as 36-character strings; money columns use BigInteger; timestamps use timezone-aware DateTime. Consent `application_id` is nullable String until an application migration adds its FK. Do not rewrite consent rows: create new grants.

`app.companies.FIXTURES` is the immutable JSON dataset and `SOURCES` maps whitelist INN to synthetic source fixture. Those internal fixtures contain later BKI/held-out oracle data: **never return or persist the whole fixture as a precheck or client payload**. `append_precheck(db, company, source, now) -> Precheck` explicitly copies only registry and turnover fields, no BKI. Internal `company_version` uniquely sequences snapshots per company so tied test clocks cannot return the wrong snapshot; it is omitted from the public API. `latest_precheck(db, company_id) -> Precheck`, `company_result(db, company) -> {company,precheck}` retrieve the latest version. No source GET consumes/retries a mock response.

`create_company(db, owner_id, source, now, *, seeded=False) -> Company` inserts company, precheck and both onboarding consent grants after endpoint validation. Seeded records use stable fixture IDs/reference date; freshly onboarded companies use UUID4/current UTC business date. `seed_demo(db, *, demo_mode: bool) -> None` from `app.seed` is idempotent, refuses false, and creates the published synthetic credentials and default client-owned fixtures. It does not reset existing data/passwords.

Implemented routes: auth register/login/logout/me; GET consent documents for onboarding/application; companies list/create/read; GET precheck; POST precheck/retry; GET `/demo/fixtures` (demo-only, client-only, safe summary excluding oracle); GET `/health` (DB ping and demo mode). Empty lists use `{items,total}`. Officer client routes return 403; there is no placeholder application/catalog API.

The retry command locks the owned Company, looks up `IdempotencyRecord` on `(actor_id,method,path,key)`, compares canonical request SHA-256, returns the saved JSON before revision validation on an exact replay, then checks version, applies immutable fixture recovery, appends precheck and increments company version exactly once in the same transaction. PostgreSQL lock and uniqueness constraints serialize concurrent calls. Future application commands should use that same ordering but lock the application row and scope ownership through Company. Replay response/status fields and resource ID are available on the shared model; do not reuse an idempotency key across different bodies.

## Validation and errors

`app.schemas.StrictModel` rejects unknown keys; extend it for every JSON body, including empty command objects. `CompanyInput` validates string-only ASCII INN/checksums and both literal JSON-true consent entries at `demo-consent-v1`. `VersionInput` requires a strict positive integer.

`app.errors.ApiError(status: int, code: str, message: str, *, fields: dict|None=None, details: dict|None=None)` renders `{error:{code,message,fields?,details?}}`. Raise it for domain/auth failures; Russian human messages, English codes. Validation errors use 422 `VALIDATION_ERROR` with paths but never echo input/secrets. DB uniqueness races map to 409 `RESOURCE_CONFLICT`; domain duplicate checks use `EMAIL_EXISTS`/`COMPANY_EXISTS`. Other errors include `ORIGIN_FORBIDDEN`, `AUTH_REQUIRED`, `CLIENT_REQUIRED`, `OFFICER_REQUIRED`, `REGISTRY_NOT_FOUND`, `COMPANY_NOT_FOUND`, `PRECHECK_NOT_FOUND`, `VERSION_CONFLICT`, `IDEMPOTENCY_CONFLICT`, `INVALID_CREDENTIALS`, `LOGIN_RATE_LIMIT` (429). Unknown routes use standardized 404. Unexpected errors use a generic 500 without stack traces in the response.

## Frontend

`frontend/src/api.ts` exports `request<T>(path: string, options?: {method?: string; body?: unknown; idempotencyKey?: string; signal?: AbortSignal}) -> Promise<T>`, where path is relative to `/api/v1`. Uses `credentials:'same-origin'`, JSON, optional key; 204 resolves undefined. `ApiError` has `status`, `code`, `message`, `fields`, `details`; network errors use status 0 and code `NETWORK_ERROR`. Aborted requests retain AbortError. No local/session storage or auth-token JSON.

Typed `User`, `Company`, `Precheck`, `CompanyResult`, `Fixture`, `ConsentDocument` and `api` helpers are exported. Extend these for later vertical slices. App session restoration uses `/auth/me`; selected company/intent appears in URL query for deep links and reload. React stores only transient form/view copies. Consent acceptance is explicit for each required server-delivered text. Read helpers `me(signal?)`, `companies(signal?)`, `company(id, signal?)`, `fixtures(signal?)`, and `consents(signal?)` accept an optional AbortSignal. The workspace cancels obsolete reads and checks a session/view generation before every asynchronous success/error/loading cleanup. Navigation invalidates the view; logout/account replacement also clears all account-bound state and invalidates the session. Initial `/auth/me` restoration has a separate controller and session-only lifetime, so company history traversal cannot cancel boot. Mutations are allowed to finish server-side, but obsolete results cannot replace the current view. Retry retains its key **and original body revision per company** across navigation or a transient network failure, and removes that attempt only after a confirmed response in the same session. The UI displays source labels, inactive/read-only status and missing information without inventing financial limits or approval claims.

## Task 3 — catalog and preliminary recommendation snapshots

- `GET /api/v1/catalog` (public, read-only reference data) returns `{catalog_version,rules_version,notice,products,research_items}`. `products` is exactly `data/demo-products.json`: the only three entries with `can_apply=true`. `research_items` is the archived research catalog (nine entries, `can_apply=false`). Three archive entries reuse the ids of supported products with different, unverified parameters; the archive never feeds a calculation, and no recommendation item or application can be built from it. No company source data is exposed.
- `POST /api/v1/companies/{id}/recommendations` accepts strict `NeedInput` from `app.recommendations.schemas` (purpose, funding pattern, amount ≤150,000,000, term 1–120, optional collateral; unknown keys such as rates or limits are 422) and returns 201 `{snapshot_id,catalog_version,rules_version,items,created_at}`. Requires CLIENT, exact Origin and an owned company; no idempotency key by design, because each calculation is an independent immutable snapshot. It locks the company row while selecting its latest persisted precheck, so a concurrent retry cannot produce mixed source versions. It makes no registry/turnover/BKI source call, does not score, and requests no consents.
- `GET /api/v1/companies/{id}/recommendations/{snapshot_id}` returns the exact saved result, scoped through the company plus a second snapshot-company predicate. Missing or foreign snapshots return 404 `RECOMMENDATION_NOT_FOUND`; a foreign company returns 404 `COMPANY_NOT_FOUND`. There is no update/delete API or TTL. A snapshot keeps the catalog/rules versions it was computed under and is never recomputed from live policy.
- Pure `app.recommendations.service.recommend(company: dict, precheck: dict, need: dict, products: list[dict]) -> list[dict]` reads only the company's `registry_status`/`entity_type`, the precheck's `monthly_revenue_rub`, the need and the policy dicts; it has no dependency on source fixtures, BKI or scoring (extra keys such as `credit_history` are ignored). Every number comes from the policy: nothing is a code constant.
  - `indicative_limit_rub = min(amount_max_rub, low_risk_revenue_multiple × monthly revenue)`; secured products are further capped by `floor(declared value × collateral_ltv_bps / 10000)`. Unknown or zero turnover, or a secured product without declared collateral, gives `null` (never 0); a declared 1 RUB yields a computed 0.
  - Status: any failed check is `does_not_fit`; otherwise any unknown check except the advisory `funding_pattern` is `needs_info`; otherwise `fits`. A different funding pattern is advisory, never a prohibition or a data prerequisite. `can_apply` needs `company_active`, `entity_type`, `purpose`, `term`, `amount_min` and `catalog_max` to pass; a capacity shortfall or missing turnover/collateral still allows a draft. An unconfirmed registry keeps the indicative numbers but blocks `can_apply`; an inactive company is read-only with a failure reason.
  - Order is the ascending tuple (status, purpose mismatch, preferred-pattern mismatch, amount shortfall with unknown capacity counted as the whole request, collateral required, `annual_rate_bps`, `product_id`) and does not depend on input order. `rank` is 1-based over the three supported products; research entries are never ranked.
  - `estimated_payment_rub` is calculated on `min(requested, limit)` when the limit is known, that amount is at least the product minimum and the product is not plainly incompatible (inactive company, or purpose/term/amount-range check failed). Term loans use the Decimal annuity rounded half up; the revolving line shows monthly interest at full utilization rounded up, with principal at maturity. Otherwise it is `null` and `payment_note` states why (inactive company, incompatible parameters, unknown limit and which data is missing, or an estimate below the product minimum). The note otherwise lists the amount, term and assumptions (no fees, minimum draw and renewal from the policy, collateral review for secured products).
  - Every item's `reasons` include «Предварительная оценка по обороту, не предодобрение. БКИ не запрашивалось.»; secured items add that founder ownership is not guarantor consent. `alternatives` suggest a supported amount, term, purpose or amount range, the data to supply, or a registry retry; an inactive company gets a single pointer to an active one.
- `app.recommendations.models.RecommendationSnapshot` extends shared Base. Migration `6ca90a120ab3` follows `070eeaa75839`: ID, company/precheck FKs, need JSON, input_snapshot JSON `{company,precheck}` (explicit precheck-only safe source subset), result JSON array, catalog/rules versions and UTC created_at (verified on PostgreSQL: upgrade from empty, `alembic check` without drift, downgrade/upgrade round trip). The application milestone should import this model, ownership-check via company, retrieve the selected product from `row.result`, compare catalog/rule versions, and use `row.id` as `recommendation_snapshot_id`. Submission must recheck fresh sources; this estimate does not authorize submission or promise capacity.
- `app.recommendations.catalog.CATALOG` loads `data/demo-products.json`, `RESEARCH` loads the archived catalog. Product policies remain server-owned; unknown request keys cannot override them.
- Frontend `Need`, `Product`, `Catalog`, `Recommendation`, `RecommendationSnapshot`, `recommendationsApi.catalog(signal?)`, `.calculate(companyId,need,signal?)`, `.snapshot(companyId,snapshotId,signal?)` are exported from shared `api.ts`. The UI does not claim to restore an edited need from a snapshot: read-only snapshot retrieval is available for the next application milestone.

### Dialog stage/field contract (`stages.py`)

`GET …/dialog` → `{application_id, status, version, current_stage, steps_total: 6, company, product, stages:[{number, title, fields:[descriptor], complete}], answers, missing_fields, field_issues:{path: message} (drafts only), allowed_actions}`. A stage is complete when none of its fields blocks submission.

| Stage | Answer fields (flat object; only `collateral` nests) | Required at submit |
|---|---|---|
| 1 Компания | `company_confirmed`, `actual_address`, `actual_activity` | true; non-blank address/activity ≤300 |
| 2 Параметры | `purpose`, `funding_pattern` (optional), `requested_amount_rub`, `term_months`, `collateral` | present and within the product (R1); secured: `collateral.status=declared` with `type`, `declared_value_rub`, `description` |
| 3 Бизнес и финансы | `monthly_revenue_rub`, `previous_monthly_revenue_rub`, `financial_period_end`, `tax_regime` (`OSN|USN|PSN|OTHER`), `employees`, `seasonal` (optional) | all but `seasonal` present (≥0) |
| 4 Обязательства | `monthly_debt_payment_rub`, `tax_debt_rub`, `legal_proceedings`, `obligations_note` (optional, ≤1000) | amounts ≥0, boolean |

| 6 Проверка и согласия | `accuracy_confirmed` | true; consents go to submit (texts from `GET /consents/documents?stage=application`, unchecked by default) |

Descriptor keys: `name, label, type (boolean|text|enum|integer|date|collateral), required`, and as applicable `must_be_true, max_length, min, max (product bounds for amount/term), options [{value, label}] (purpose options are the product's purposes), statuses, types, description_max_length`. Stage-3 finance fields add `source {name:'turnover', status, value}` and `origin` (`source` = equals the source, `override` = differs from a known source value, `declared` = the source has no value, `null` = no answer). Paths in `missing_fields`, `field_issues`, error `fields` and InfoRequest `requested_fields` are answer names, `collateral.<key>` for pledge details. Creation prefills stage 2 from the snapshot need and stage 3 from the latest precheck; the debt payment is never prefilled (client-declared). `stages.merge(answers, patch)` replaces top-level fields and merges collateral keys; null clears.

### Transition service and load helpers (`lifecycle.py`)

- `ApplicationChange(db, application, *, actor_id, now)`: `.touch()` = same-state edit (version +1 once per command, `updated_at`); `.move(to_status, *, reason_code, reason_text, notification=None, by_system=False) -> StatusHistory` validates against `TRANSITIONS` (409 `INVALID_STATUS` otherwise), increments the version once per command, appends StatusHistory (internal per-application `sequence`, `application_version` = resulting revision) and its Notification (`event_code` `application_<status>`, default text `NOTIFICATIONS[status]`). `by_system=True` records actor null. `record_creation(db, application, *, actor_id, now)` writes the initial null→DRAFT row. Tasks 5 and 6 change statuses only through `move`.
- `TRANSITIONS`: DRAFT→CHECKING/CANCELLED; CHECKING→WAIT_EXTERNAL/NEED_INFO/MANUAL_REVIEW/PREAPPROVED/REJECTED; WAIT_EXTERNAL→CHECKING/CANCELLED; NEED_INFO→CHECKING/MANUAL_REVIEW/CANCELLED; MANUAL_REVIEW→NEED_INFO/PREAPPROVED/REJECTED/CANCELLED; PREAPPROVED→DOCS_UPLOADED/REJECTED/CANCELLED/EXPIRED; DOCS_UPLOADED→DOCS_REWORK/APPROVED/REJECTED/CANCELLED/EXPIRED; DOCS_REWORK→DOCS_UPLOADED/REJECTED/CANCELLED/EXPIRED; APPROVED, REJECTED, CANCELLED, EXPIRED terminal. `CANCELLABLE` is derived from it.
- `expire_if_due(db, application, now) -> bool`: PREAPPROVED/DOCS_UPLOADED/DOCS_REWORK → EXPIRED (system, `PREAPPROVAL_EXPIRED`) once `now >= preapproval_expires_at` (= `preapproved_at + PREAPPROVAL_TTL`, 14 days, set at preapproval); re-reads the row `FOR UPDATE`, so concurrent readers record exactly one expiry. Call it right after loading.
- `get_owned_application(db, id, user_id, now)` (owner read, 404, lazy expiry); `lock_owned_application(db, id, user_id, now) -> (application, company, expired_now)` (owner command: company row lock, then application row lock, then lazy expiry; the fixed order serializes commands per company); `owned_applications(db, user_id, now, *, status=None, company_id=None)`.

### Idempotency helper (`app/idempotency.py`)

`IdempotencyKey` (required `Idempotency-Key` header, 1–128), `scope_of(request, actor_id, key, body_model) -> Scope` (actor, method, path, key, SHA-256 of the canonical JSON body), `replay(db, scope) -> JSONResponse | None` (stored status and body; 409 `IDEMPOTENCY_CONFLICT` on another body), `remember(db, scope, body, *, now, status=200, resource_id=None) -> body`. Lock and check ownership first, replay before version/state validation, store only 2xx results. `POST /companies/{id}/precheck/retry` now uses it unchanged in behavior.

### Check, BKI simulator, scoring and InfoRequests

- `checks.run_check(db, change, company, product) -> Evaluation` runs on a CHECKING application under the command's locks: reads the latest precheck (never calls registry/turnover mocks), builds `scoring.CheckInput`, calls `scoring.before_bki`; only if that returns None it makes exactly one `bki.request_report(company.inn, attempt)` and calls `scoring.after_bki(check, report, trusted_source_review=<open trusted_source request>)`. It stores an immutable Evaluation (`input_snapshot` with finance evidence, scored answers, age, review flags; `sources` with registry/turnover precheck ids and the BKI payload), opens or reuses a system InfoRequest, resolves an open bki request when a complete report arrives, sets `scored_limit_rub` (and, on PREAPPROVED, `preapproved_amount_rub`, `preapproved_at`, `preapproval_expires_at`) and moves to the outcome as a system step. An information response is re-checked without a new BKI request by `checks.recheck_after_response` (Task 5a, below).
- `bki.request_report(inn, attempt) -> {provider, synthetic, attempt, status: available|missing|unavailable, credit_history, current_overdue_days}` reads only those categories from the whitelisted fixture; attempt 1 uses `bki_source_status`, later attempts `recovery.retry_*`. `checks.bki_attempts(db, application_id)` derives the attempt from persisted evaluations, so recovery survives a restart. `bki.CALLS` is the observable in-process call log (tests assert zero calls before consent, during recommendations and on replays, one per submit/retry).
- `scoring` (pure): `completed_months`, `score_of(age, R, P, debt, history) -> (score, factors)`, `risk_of`, `scored_limit(product, risk, R, collateral)` (low `min(ceiling, 3R)`, medium `min(ceiling, 1m, R)`, high none, secured `floor(value×7000/10000)`; numbers from the policy), `before_bki` (R2 known inactive → R3 client gap with a client_answers request → R4 registry/turnover unavailable), `after_bki` (R4 BKI unavailable → R2 overdue ≥30 → R3 missing category with a trusted_source request → R5 review flags `zero_revenue, invalid_source, declared_finance, finance_override, collateral_unconfirmed, tax_debt, legal_proceedings, registry_unconfirmed` → R6 → R7 → R8/R9 PREAPPROVED, R10/R11 MANUAL_REVIEW; trusted-source recovery: R2/R6/R7 reject, otherwise MANUAL_REVIEW with the computed rule recorded). `Decision` carries rule, outcome, reasons, score, risk, factors, scored limit, preapproved amount, flags and an optional InfoRequest spec.
- Stage-3 evidence (`stages.finance_evidence`): a known source value stays authoritative and is the scored value; an override keeps both values and routes R5; a declared value (source without one) is scored and routes R5.
- Business age: completed months from `company.registered_at` to `company.business_reference_date` (fixture date for seeded companies, onboarding date otherwise).
- `info_requests.create_info_request(db, application, *, kind, source, requested_fields, question, now, officer_id=None)` enforces trusted_source (source in registry/turnover/bki, no officer, no fields) versus client_answers (no source, non-empty answer paths from `ANSWER_PATHS`; officer requests pass `officer_id`); `open_info_request(db, application_id)` returns the unresolved one. Task 4 creates system requests only (`officer_id` null); Task 5a adds officer requests and respond-info.
- `companies.recover_precheck(db, company, now) -> Precheck`: the fixture recovery lookup extracted from the company retry (appends a precheck, company version +1); retry-check calls it once when the latest precheck has an unavailable registry or turnover source, then runs the check under the policy pinned at submission and the stored BKI consent.

### Customer endpoints (CLIENT owner: another client 404 `APPLICATION_NOT_FOUND`, an officer 403 `CLIENT_REQUIRED`, except the download; mutations need the exact Origin and an `Idempotency-Key` header)

| Method/path | Body → success | Errors, in check order |
|---|---|---|
| GET `/applications/{id}/documents` | → `{notice, requirements:[{document_type, required: true, current_document: document \| null}], items:[document]}`; `notice` is the «Демонстрационная проверка документов…» label (no antivirus or authenticity claim); `items` are every revision in checklist order, then revision; lazy expiry applies | 404 |
| POST `/applications/{id}/documents` | multipart: `file` (with a file name), `document_type`, `version` (decimal string) → 201 `{document, application}`; the ownership read's transaction ends before the body streams (no pooled connection is held), and the command runs at the time the body has arrived (`clock.request_clock`), so lazy expiry and `created_at` use that time | 401/403 (session, role, Origin), 422 (missing key header), 404 `APPLICATION_NOT_FOUND` (checked before any byte is read), 413 `FILE_TOO_LARGE` (while reading), 422 `VALIDATION_ERROR` (not multipart, missing/unknown/repeated parts, a second file, an empty file name, a part header above 4 KiB or more than 8 headers in a part, unknown `document_type`, `version` not a positive integer), 415 `MEDIA_NOT_ALLOWED` / 422 `FILE_INVALID` (file rules below), replay or 409 `IDEMPOTENCY_CONFLICT`, 409 `APPLICATION_EXPIRED` (committed), 409 `VERSION_CONFLICT`, 409 `INVALID_STATUS` (only PREAPPROVED and DOCS_REWORK), 422 `DOCUMENT_TYPE_NOT_ALLOWED` (`fields.document_type`: not in the product's checklist), 409 `DOCUMENT_ACCEPTED` (the current revision is accepted) |

| DELETE `/applications/{id}/documents/{doc_id}` | `{version}` → `{application}`; the revision becomes DELETED, its bytes go after the commit | 404 `DOCUMENT_NOT_FOUND` (not this application's; before the replay), replay, 409 `APPLICATION_EXPIRED`, 409 `VERSION_CONFLICT`, 409 `INVALID_STATUS`, 404 `DOCUMENT_NOT_FOUND` (already deleted), 409 `DOCUMENT_ACCEPTED`, 409 `DOCUMENT_NOT_CURRENT` (a superseded revision) |

Uploads and deletions are same-state edits (version +1, no history row, no notification) and never move `preapproval_expires_at`. Upload digest for idempotency: `{document_type, version, sha256 of the received bytes, stored original_name}`. A replacement supersedes an UPLOADED or REJECTED current revision (its row, reason and bytes stay as audit evidence); an ACCEPTED revision is never replaced or deleted, also not after approval (uploads/deletes are refused in every state but PREAPPROVED and DOCS_REWORK).

File rules (`validation.py`; a structural demo check, not antivirus scanning): the stored `original_name` is the last path segment of the sent name, NFC, without control/format characters (category C, bidi overrides included), whitespace collapsed, at most 200 characters keeping the extension (percent escapes are not decoded). Then, in order: the extension (`pdf`, `jpg`/`jpeg`, `png`) and the part's MIME type must name the same allowed type (415); an empty file is 422; the magic bytes must agree (415); HTML/SVG/script markup anywhere (`<script`, `<html`, `<svg`, `<iframe`, `<object`, `<embed`, `<body`, `<!doctype`, `javascript:`) is 415; pypdf strict open with ≥1 page and no encryption, or Pillow `verify()` then a full `load()` within 40 megapixels (checked from the header before decoding; it replaces Pillow's own decompression-bomb guard, `Image.MAX_IMAGE_PIXELS = None`, so no image above the budget is decoded or warned about), else 422; PDF active content — JavaScript, JS, OpenAction, AA, Launch, EmbeddedFiles, RichMedia as a name anywhere in the parsed objects (hex escapes and object streams included) or as a raw token in the bytes outside stream bodies (stream data is skipped: compressed or binary data matches such tokens by chance) — and any data after the format's end (PNG IEND, JPEG EOI, only whitespace after the last PDF `%%EOF`) are 415. The size limit is 20 MiB (20,971,520 bytes) for the file part, with a 64 KiB envelope for the whole body; a declared larger Content-Length is refused before reading.

### Public document and summary

Document: `{id, application_id, document_type, revision, original_name, media_type, size_bytes, sha256, status (UPLOADED|ACCEPTED|REJECTED|SUPERSEDED|DELETED), review_reason, verified_value_rub, created_at, reviewed_at, download_url (null once DELETED)}` — never `storage_key` or the reviewer's identity (the staff document adds `reviewer {id, display_name} | null`). `application.document_summary` is null before preapproval (`preapproved_at` null), otherwise `{required_total, current_uploaded, accepted, rejected, missing:[types], can_complete}`: `current_uploaded` counts requirements with a current revision whatever its review, `accepted`/`rejected` those reviewed so, `missing` the requirements without one, `can_complete` only in PREAPPROVED/DOCS_REWORK with nothing missing or rejected. Customer `allowed_actions` gain, before `cancel` and only in PREAPPROVED/DOCS_REWORK: `upload_document` (some requirement is not accepted), `delete_document` (some current revision is UPLOADED or REJECTED), `complete_documents` (nothing missing or rejected).

A review records reviewer, time, trimmed reason and (an accepted valuation only) the verified value on the Document row in one step; it writes no OfficerDecision. Accepting is a same-state edit (version +1, no history). The first rejection moves DOCS_UPLOADED→DOCS_REWORK (officer step `DOCUMENT_REJECTED`, `reason_text` = the reason; notification «Документ «…» нужно заменить…»); the other documents wait for the next DOCS_UPLOADED. `policy.final_terms` reads only persisted evidence: every required type's current revision must be ACCEPTED; the limit is recomputed with `scoring.turnover_limit` from the latest evaluation's risk and scored revenue and, for the secured product, capped by `scoring.collateral_cap` of the accepted COLLATERAL_VALUATION's `verified_value_rub` (the same helpers `scoring.scored_limit` applies to a declaration) (never the client's declaration or an approve-request value); bounds are `product.amount_min_rub ≤ final ≤ min(preapproved_amount_rub, that limit)`, inclusive, and a bound below the minimum refuses approval so that only a reasoned final rejection remains (no system rejection). Approval writes `OfficerDecision(final, approve, amount)` and the officer step `FINAL_APPROVED` with the notification «Заявка одобрена на … (демонстрационное решение). Деньги не перечисляются, договор не подписывается.» APPROVED never expires.

Staff application (queue, detail, command results) adds `document_summary` and `final_approval` (DOCS_UPLOADED only, else null): `{amount_min_rub, amount_max_rub, verified_limit_rub, blocked_by: null | {code: DOCUMENTS_NOT_ACCEPTED|LIMIT_NOT_COMPUTABLE|COLLATERAL_INSUFFICIENT|LIMIT_BELOW_MINIMUM, message}}` (bounds null when blocked; `verified_limit_rub` is shown for a below-minimum refusal). Staff `allowed_actions` gain, for the assignee in DOCS_UPLOADED, `review_document` (a current revision is UPLOADED) and `approve` (final terms not blocked), before `reject`. Staff detail `documents` is every revision (staff documents, checklist order, then revision), `document_notice` is the same «Демонстрационная проверка документов…» label as the customer checklist's `notice`, and the new top-level `requestable_fields` lists `info_requests.OFFICER_PATHS` for the product (pledge paths only for the secured product; the need fields never).
