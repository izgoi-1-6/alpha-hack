## Authentication and common HTTP contract

All endpoints start `/api/v1`. UUID strings identify entities; `product_id` and fixture IDs are the stable strings in data. Dates ISO-8601; timestamps UTC `Z`. API reads return objects, lists `{items:[...],total:N}`. Error shape `{error:{code,message,fields?,details?}}`; message is Russian. `fields` maps field paths to messages; never include stack traces or secrets. Unknown request keys are rejected (422), including role/status/owner injection. Use 401 unauthenticated, 403 wrong role/origin, 404 absent or other customer's resource, 409 state/version/duplicate/idempotency conflict, 422 invalid data, 413 oversized file, 415 unacceptable media.

Server-owned opaque random session cookie `credit_route_session`, HttpOnly, SameSite=Lax, Path=/, Secure in HTTPS (false only documented localhost development). Store only a hash of the token, never return token JSON; no browser auth storage. Sessions expire 12h after login (no sliding refresh), revoke on logout, new login creates a new session. Hash passwords with a maintained password library. Email trim/lowercase, unique; password 10–128 characters. Registration creates CLIENT only. Officer seeding only via demo tooling; no role picker in public registration. Authenticated mutating requests require Origin matching configured exact UI origin; absent/foreign Origin fails 403 (integration drivers send it). CORS permits only configured development origin with credentials; Vite/production proxy presents same origin to browser.

|---|---|---|
| POST `/auth/register` | `{email,password,display_name}` (name 1–100 chars) | 201 `{user}` + cookie |

`user` contains only `{id,email,display_name,role}`. Apply Origin check to registration/login too. Limit login attempts in demo reasonably; do not claim production abuse protection. Demo-only seed creates `client@demo.local`, `other@demo.local`, `officer@demo.local`, password `DemoCredit2026!` (published synthetic local credentials, never production secrets). IDs in fixture actors are stable seed IDs. Both clients get no cross-access; default fixture companies belong to the first client. Seed is idempotent, gated by demo mode; production refuses demo seed/reset.

For application edits and stateful commands body `version` is the current integer revision (starts 1); successful changes increment it once. No need to use ETag/If-Match as well. Stateful POST commands require `Idempotency-Key` (1–128 characters); scope `(actor_id,method,path,key)` with body digest, persisted status/body and resource ID. Exact replay returns the original result without new evaluation/history/BKI call; same key + different body → 409 `IDEMPOTENCY_CONFLICT`. Replay lookup precedes version/state validation but follows authentication/ownership checks. Keys survive for the lifetime of the demo database. Commands serialize on application row/conditional version update; DB uniqueness also guards active submissions. Upload uses version and key form fields/header; downloads/reads never change revision except lazy expiry.

## Company onboarding and precheck

INNs must be strings of ASCII digits, length 10 LLC / 12 IP, valid standard Russian checksums. Ten digits: weights `[2,4,10,3,5,9,4,6,8]`, mod11 mod10. Twelve digits: digit11 uses `[7,2,4,10,3,5,9,4,6,8]`; digit12 uses `[3,7,2,4,10,3,5,9,4,6,8]` including digit11. Reject all-identical-digit and all-zero numbers even if checksum holds. Infer type from length. An INN may be onboarded by separate synthetic users, each with their own verification, but is unique per owner. Whitelisted fixtures are immutable source data, separate from application answers.

Authority check (revision rule 6). Adding a company requires a mock Госуслуги verification of the session user for that INN. The mock always confirms a whitelisted INN with the fixture's synthetic director as the person; a real ЕСИА check would refuse a user who does not represent the company, which this demo does not model, so several users may confirm and add the same INN. A verification adds one company within 30 minutes of `verified_at` (valid strictly before `expires_at`); the company stores it, its questionnaire takes the representative from it, and submission re-checks it. The seed records a verification (`method=seed`, already used) for each seeded company. No real redirect, ЕСИА/Госуслуги API, logo or trademark is used.

## Product policy and recommendations

Revision 2026-10-25 (plan Task 8) replaces the three-product demo policy; editing and validation are described in `docs/catalog.md`.

**Configuration.** `data/credit_catalog.json` (schema 3.2, `catalog_version` `2026-10-25.1`) is the user's catalog plus per-card explanation texts (`display.summary`, 3–5 `display.features`, `display.best_for`, drafted only from the item's own facts), `amount.max_unsecured` and `term.max_months_by_purpose`; it is authoritative for amounts, terms, rates, purposes and eligibility. `data/demo-policy.json` (`demo-rules-v2`) holds the demo decision rules and the fallbacks for catalog nulls: a per-product setting, else a default. The policy may tighten a stated catalog value but never weaken it (`collateral.required: true` stays required). `app.products_config` validates both files at start-up — the app refuses to start on any problem, every problem reported with its path — and builds the one runtime product model every consumer reads. `python -m app.products_config check [--catalog P] [--policy P]` validates edits; `CREDIT_CATALOG_PATH` / `DEMO_POLICY_PATH` override the files. Versions are stamped `catalog_version+sha8(file)` and `rules_version+sha8(file)`, so any edit, even without a version bump, makes earlier snapshots and drafts stale. Each catalog item of kind `product` or `gov_program` with `display.as=card` is a card product, shown and evaluated; it accepts applications when `status=active` and `limit_status=open`. `overlay` items are badges only. `data/catalog.research.json` is history and never read. Product maximum ≠ indicative personal limit ≠ preapproved amount ≠ final amount.

Rates: a `rate_formula` (`KEY_RATE`, `KEY_RATE ± n` or a number, parsed without eval) must equal the item's `rate_percent` at `params.key_rate`; certainty is `full`, `preferential` (the rate period ends before the product's longest term: the payment is labelled «в льготный период N мес.») or `undisclosed` (no payment, «Ставка уточняется»). Payment models by instrument type: term loan and non-revolving line → annuity; revolving line → interest at full utilization; factoring → none.

**Need.** `{requested_amount_rub}` only: a strict integer from 1 to the slider maximum (2,000,000,000); unknown keys are 422. Purpose, term and collateral are chosen in questionnaire stage 2 within the chosen product's bounds; `funding_pattern` is not part of the need.

**Eligibility.** Only machine-checkable rules apply: entity type (catalog ИП→IP, ЮЛ→LLC); `msp_registry_required` against the company's SME-register flag; `regions_allow` against the company region, both normalised (casefold, ё→е, collapsed spaces); `okved_deny_main` entries whose text starts with a two-digit class `NN` or a range `NN–NN`, compared on the main OKVED class (`alfa_goscredit_zont` denies 05–09, 64–66 and 92; «производство и продажа подакцизных товаров (кроме ОКВЭД 55, 56)» bans nothing, and an entry that starts with a subclass such as `47.11` is informational). Unparsed OKVED text, `categories` and `requirements` are `conditions_to_confirm` (`{kind: requirement|category|okved, text}`): shown, never blocking, never forcing review.

Pre-submission recommendations MUST NOT call BKI, use credit history, compute a score or state an approval probability. Checks `{code,result:"passed"|"failed"|"unknown",text}`, in order: `company_active` (registry active / unknown / inactive), `entity_type`, `msp_registry` (unknown while the registry is unconfirmed), `region`, `okved` (unknown without a main OKVED when the product denies classes), `program_status` (status active and limit open), `amount_min`, `catalog_max`, `turnover` (unknown or zero turnover → unknown), `collateral` (none/optional pass; required → unknown: the pledge is declared in the questionnaire), `amount_capacity`. Any failed check → `does_not_fit`; else any unknown → `needs_info`; else `fits`. `can_apply` requires `company_active`, `entity_type`, `msp_registry`, `region`, `okved`, `program_status`, `amount_min` and `catalog_max` to pass; capacity, turnover and collateral gaps never block a draft. Indicative personal limit with positive known monthly turnover R: `min(product max, 3R, unsecured cap)`, where the unsecured cap is 0 for a product that requires collateral (so its limit stays null until the questionnaire), `max_unsecured` for the universal limit and the product maximum otherwise; no product bypasses turnover, unknown/zero turnover gives null. An unconfirmed registry prevents `fits` but keeps the indicative numbers. The estimate is labelled «Предварительная оценка по обороту, не предодобрение».

The indicative payment is computed on `min(requested, limit)` when the limit is known, that amount is at least the product minimum, the company is not inactive and no product condition failed: the Decimal annuity rounded half up over the policy's `payment_estimate_term_months` (36) clamped to the product's term range, or `ceil(A×bps/120000)` monthly interest with the principal at maturity for a revolving line. Otherwise it is null and `payment_note` says why. `badges[]` (`{overlay_id,name,text}`): an overlay shows on a card it `applies_to` when the company is in the SME register and its main OKVED is known and not denied (the policy exempts `psk_borderline` from the umbrella's 47 rule, per the overlay's process note); a card whose collateral is required gets the policy's softer text.

Ranking ascends by (status fits/needs_info/does_not_fit; known shortfall `max(0, requested − limit)`, an unknown limit counting as the whole request; collateral burden none 0 / optional 0 / required 1; rate certainty full 0 / preferential 1 / undisclosed 2; annual rate bps, undisclosed counting as 0; the policy's product priority; product id). A preferential first-year rate therefore never outranks a stated full-term rate. Ranks are 1-based over every card product; reasons and alternatives are returned even if none fits.

Recommendation item: `{product_id,rank,status,can_apply,indicative_limit_rub,catalog_max_rub,requested_amount_rub,checks,reasons,alternatives,estimated_payment_rub,payment_note,payment_label,badges,conditions_to_confirm}`.

Creating an application copies its owned snapshot (no TTL on draft creation) and prefills stage 2 with the need's amount, plus the purpose when the product has only one; term and collateral start empty for the client. Submission rechecks current source data and the company's eligibility (R1) and pins the runtime product with its effective terms, `secured`, `required_documents` and the stamped versions, so old estimates do not promise capacity (see «Pinned decision facts»). **Personal limit (one formula).** Every limit — the card's indicative estimate (low risk, no pledge known), the scored and indicative limits of a submitted application, the officer's preapproval bound and the final bound — is `min(effective max, T, secured ? unsecured cap + ⌊LTV·V⌋ : unsecured cap)` (`app.products_config.limits`). T is `min(max, 3R)` at low risk and `min(max, 1,000,000, R)` at medium risk (for every product, gov programs included: a 25,000,000-minimum program therefore needs low risk); high risk or no positive turnover gives none. The unsecured cap is 0 when collateral is required, `max_unsecured` for the universal limit (20,000,000) and the effective maximum otherwise. V is the declared pledge before the document review and the accepted valuation's verified value at final approval; a secured application without a positive V has no limit. Factoring has no catalog maximum (the 2,000,000,000 fallback), so its capacity is the turnover limit.

**Pinned decision facts.** Submission pins into the submission snapshot: `product` (the runtime product with its effective terms, collateral mode, rate, payment model and the policy's multiples, LTV and documents), `secured` (collateral mode `required`, or `optional` with `collateral.status=declared`) and `required_documents` (the base documents, plus the collateral documents when secured). Every later reader — scoring on retry and after an information response, R5's `collateral_unconfirmed`, the documents checklist, the officer's requestable fields, preapproval and final bounds — uses the pinned facts, never the live product; a submitted application without them fails loudly (no legacy adapter: applications submitted before revision Task 9 were removed with the dev database). An information response never makes an application secured or unsecured. The evaluation input snapshot records `secured`, the product summary shows `secured`, `payment_model` and `required_documents`, and the officer's submitted evidence lists `secured` and `required_documents`.

Stage 2 follows the chosen runtime product: `purpose` options are its purposes (a single purpose is preselected), `requested_amount_rub` carries its `min`/`max`, `term_months` its range with `max` lowered for the saved purpose and `max_by_purpose` (the field is absent for a product without a term), and `collateral` is `required` (mode required), optional (mode optional) or absent (mode none). An answer accepts amounts up to the policy maximum (2,000,000,000) and terms of 1–120 months; each product's bounds are checked at submission. `funding_pattern` is gone. Wizard prefills source finances and the need's amount; user confirms or edits. Overrides of known source finances or nonzero tax debt/legal proceedings route R5 manual review; flag sources and original values, never erase originals. Unknown source finances may be supplied as declared (source tag retained), yielding MANUAL_REVIEW even if score is low until officer checks evidence. Zero previous/current revenue is allowed as saved data but routes R5 (no division, no auto-limit). Negative numbers are invalid input, yet malformed imported internal data is R5. Requested amount above personal capacity is allowed within product ceiling; R9/R11 handles it.

## Scoring and state machine

Original factors (RUB values compare with exact integer arithmetic): business age ≥24 months 20, 6–23 10, <6 0. Revenue growth `(R-P)/P`: >10% 25; −10% through +10% inclusive 15; <−10% 0. Monthly debt/R ≤30% 30, >30% through50% 15, >50% 0. BKI history `clean`25, `minor_closed`10, `serious`0. Total≥75 low, ≥50 medium, otherwise high. `serious` historical is not itself a hard stop: current overdue≥30 days or inactive company is R2 regardless of points. No hypothetical diagnostic score is persisted as an executed evaluation. External BKI data is trusted only from configured mock; questionnaire cannot set it.

| Rule in order | Trigger | New behavior |
|---|---|---|
| R1 | the company now fails the product's eligibility (entity type, SME register, region, main OKVED class, open program; on `product_id`), or has an unknown fact for it while its registry source is available (with the registry unavailable an unknown fact waits for R4), or an unsupported purpose/amount/term (per-purpose maximum included), a term for a product without one, a declared pledge for a product without collateral, or invalid input | 422 `CORRECTION_REQUIRED`, keep DRAFT; no BKI/evaluation |
| R2 | known inactive, BKI current overdue≥30d, or a failed eligibility fact of the pinned product on the company data recovered after R4 (history reason `ELIGIBILITY_FAILED`) | REJECTED, score may remain null; bypass later rules |
| R3 | required client values (never a source-owned answer)/the secured application's pledge details/submission consents absent | submit 422 `NEED_INFO`, keep DRAFT and no BKI for missing consent; if gap discovered in submitted check → NEED_INFO |
| R4 | registry/turnover/BKI unavailable (not simply missing) | WAIT_EXTERNAL; retry explicit, no hidden loops |
| R5 | zeros/contradictory finance, imported invalid values, declared-only finance, an unconfirmed or encumbered pledge of a (pinned) secured application, tax/legal concern | MANUAL_REVIEW with evidence; score/limit null if noncomputable |
| R6 | computed score<50 | REJECTED |
| R7 | scored limit<effective product minimum (catalog, else policy fallback) | REJECTED |
| R8 | low risk and request≤scored limit | PREAPPROVED, preapproved amount=request |
| R9 | low risk and request>scored limit | PREAPPROVED, preapproved amount=scored limit; explain smaller amount |
| R10 | medium risk and request≤scored limit | MANUAL_REVIEW |
| R11 | medium risk and request>scored limit | MANUAL_REVIEW, show lower possible amount |
| R12 | assigned officer preliminary preapprove/reject | PREAPPROVED/REJECTED; never final APPROVED |

R1, known registry R2 and required consent/input R3 are checked before any BKI. Registry unavailable uses R4 (it is not missing client input): while the latest precheck's registry source is unavailable, an unknown SME flag, region or OKVED does not block R1 (a failed fact still does); the check waits (WAIT_EXTERNAL, no BKI) and, after the retry's recovery, re-evaluates the pinned product's eligibility on the current company data before any BKI request — a fact that now fails is a mandatory stop, R2 REJECTED with reason `ELIGIBILITY_FAILED` and no BKI call (a submitted application never returns to DRAFT). With the registry available, an unknown fact refuses at submission like `can_apply`. Known inactive overrides missing finance; R1 precedes R2, so an inactive company outside the SME register is corrected (R1 422) on an SME-register product and rejected (R2) on other products. After successful submission, persist consent → CHECKING/history → call BKI once → store evaluation and result within transaction/guarded service. A missing BKI result category is NEED_INFO with a system-created trusted_source InfoRequest (`officer_id=null`, `source=bki`, `requested_fields=[]`, generated retry explanation); unavailable service is WAIT_EXTERNAL. A client-answerable gap creates kind=client_answers with requested answer paths; an officer request always has kind=client_answers and nonnull officer_id. For trusted_source, source is required, officer_id is null and requested_fields is empty; client_answers uses source=null and nonempty requested answer paths. System requests may be unassigned. Source-owned gaps cannot be filled through questionnaire answers; their allowed_actions exposes retry_check, not respond_info. Retry/answers create a new immutable evaluation; preserve prior source payloads/evaluations. No real source network calls.

Allowed states, exact spelling: `DRAFT`, `CHECKING`, `WAIT_EXTERNAL`, `MANUAL_REVIEW`, `NEED_INFO`, `PREAPPROVED`, `DOCS_UPLOADED`, `DOCS_REWORK`, `APPROVED`, `REJECTED`, `CANCELLED`, `EXPIRED`.

- Create→DRAFT. Submit DRAFT→CHECKING→WAIT_EXTERNAL/NEED_INFO/MANUAL_REVIEW/PREAPPROVED/REJECTED. CHECKING is a real history step; synchronous response can return final resulting state.
- WAIT_EXTERNAL→CHECKING on retry. NEED_INFO with an open trusted_source request also permits retry-check→CHECKING using stored submission BKI consent for BKI, attempting the named mock once. Missing again→NEED_INFO; unavailable→WAIT_EXTERNAL with the request unresolved; valid fresh trusted-source evidence resolves the request (`resolved_at=now`) and creates a new evaluation, then MANUAL_REVIEW even if low risk (R2/R6/R7 mandatory rejections still apply). Preserve application ID/assignee and old evidence. Later retries from WAIT_EXTERNAL retain this return-to-review rule while that request is unresolved. No maximum-retry rejection or hidden timed loops.
- MANUAL_REVIEW→NEED_INFO on officer request; NEED_INFO with kind=client_answers→MANUAL_REVIEW when client responds, recording responded_at/resolved_at and retaining ID, previous evidence and assignee. No automatic low-risk shortcut after a requested answer; officer reviews it. `missing_fields` and `open_info_request` make recovery concrete. System-generated NEED_INFO may have no assignee, queue it on response.
- MANUAL_REVIEW→PREAPPROVED/REJECTED by assigned officer. A null/noncomputable limit forbids preliminary approval until supplied finance yields a calculable limit; rerun scoring after responses when needed. After an information response, recompute calculable score/limit from the revised answers and latest trusted source evidence, preserving original snapshots, retain all conflict/declaration flags and MANUAL_REVIEW; officer reason records resolution. Medium risk is allowed by officer; R2/R6/R7 cannot be overridden. Officer amounts satisfy product_min≤amount≤min(request,scored_limit); original requested amount is never rewritten.
- PREAPPROVED→DOCS_UPLOADED on complete checklist. DOCS_UPLOADED→DOCS_REWORK on rejected required document; DOCS_REWORK→DOCS_UPLOADED on all required documents replaced/present. Uploads do not auto-complete the packet.
- DOCS_UPLOADED→APPROVED by assigned officer only after all current required docs accepted. Final amount must satisfy product_min≤final≤preapproved and remain within verified collateral/turnover bounds. Incomplete/unaccepted docs make approval409. PREAPPROVED/DOCS_UPLOADED/DOCS_REWORK→REJECTED by assigned officer with reason; rejection does not require complete or accepted documents.
- DRAFT, WAIT_EXTERNAL, MANUAL_REVIEW, NEED_INFO, PREAPPROVED, DOCS_UPLOADED, DOCS_REWORK→CANCELLED by owner. CHECKING cancellation serializes until check transaction ends. APPROVED/REJECTED/CANCELLED/EXPIRED terminal; no edits/actions except authorized reads/downloads and approved handoff.
- PREAPPROVED, DOCS_UPLOADED and DOCS_REWORK→EXPIRED once `now >= preapproved_at+14*24h`. Deadline never extends with uploads/rework/claim. Enforce on every relevant read/command (lazy expiry plus optional scheduled sweep), append exactly one history/notification. APPROVED never subsequently expires. New application required after expiry; no revive command.

One active submitted application per company/product in CHECKING, WAIT_EXTERNAL, MANUAL_REVIEW, NEED_INFO, PREAPPROVED, DOCS_UPLOADED, DOCS_REWORK. Multiple DRAFT allowed; submission conflict 409 `DUPLICATE_ACTIVE_APPLICATION` with existing ID for same owner. DB constraint/lock enforces races, not just UI. Lazy expiry runs before duplicate check. Each state change records actor, UTC time, reason, revision and simulated notification; same-state edits/claim can increment version without inventing a status transition. No arbitrary status PATCH endpoint.

## Documents and final decision

The checklist is the application's pinned `required_documents`: `BANK_STATEMENT`, `FINANCIAL_REPORT` for every application; a secured one (collateral required, or an optional pledge declared) adds `COLLATERAL_OWNERSHIP`, `COLLATERAL_VALUATION`. These are synthetic evidence, not real bank legal requirements. Current period end from questionnaire, no hidden recency rule; officer reviews declared period and content. Each requirement has one current document; replacements supersede old metadata/content access remains authorized, rejected required document must be replaced. Accepted documents cannot be silently replaced; allow replacement of UPLOADED/REJECTED only before final state. Upload/delete allowed PREAPPROVED or DOCS_REWORK; DOCS_UPLOADED freezes packet until review/rework. Missing optional document cannot block approval. All mandatory docs must exist at complete and all must be ACCEPTED at approve. Officer acceptance of COLLATERAL_VALUATION requires positive `verified_value_rub`, persisted atomically on that Document row with ACCEPTED status/reviewer/time. Other document types and rejected/unreviewed valuation revisions keep the field null. Final approval reads the persisted current ACCEPTED COLLATERAL_VALUATION document revision and recalculates the bound with the same personal-limit formula (the evaluation's risk and scored revenue; for a pinned secured application the unsecured cap plus ⌊LTV·verified value⌋), never client declaration or a new approve-request value. That accepted revision/value is immutable and remains readable after process restart; replacement revisions start with null verified value and cannot inherit prior acceptance. If below minimum → final reject with reason, never fabricate support.

File constraints: single file ≤20 MiB, only PDF/JPEG/PNG, extension/MIME/magic/content agree; reject HTML/SVG/script/polyglot content, empty/invalid/truncated formats and executable archives. Use a maintained parser for structural validation; no claim of antivirus. Ignore upload paths; generate random private storage key outside webroot, sanitize attachment filename; cleanup failed/rolled-back uploads and handle deletion consistently. Stream with safe Content-Disposition. Maximum one current file per requirement. Retain SHA-256 of actual bytes; seeded structured oracle hashes are not file hashes. The server's review notice says «Проверка документов: …» and that it is neither an antivirus nor an authenticity check (the UI badge wording is revision Task 11). Handoff is an authenticated local page confirming simulation, no bank redirect/signing/disbursement. APPROVED does not mean money issued.
